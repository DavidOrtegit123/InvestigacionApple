## Research Design & Decisions Log

_A running log of the study design and research-scope decisions, kept separate from "Current Status" (which tracks the shipped code). Add to this only when explicitly asked, same as Current Status._

**Study design** ("Evaluating On-Device AI Backends for RAG-Grounded Code Generation: Apple Foundation Models vs. Open LLMs via Core AI," David Ortega, Tec de Monterrey):
- **H1 (primary, inferential):** Apple's Foundation Model and a small open-weight LLM (System B), both given the same retrieval-augmented prompt and structured memory — with retrieval held constant via an oracle document (the correct spec supplied in full) — achieve statistically comparable pass@1 (execution-verified code-task success) on the same task set. Primary test: Wilcoxon signed-rank on per-task pass rates (changed from McNemar on 2026-09-30, before tasks 14–40 were collected, because each task is now asked 5 times — see "Pre-specified analysis plan"); McNemar on each task's first answer is kept as a secondary check. **Result (2026-10-06): rejected — Apple's model scored significantly higher (40% vs. 13%, Wilcoxon p < 0.001); see "Main study results" below.**
- **H2 (secondary, descriptive — not statistically tested):** System B requires less storage and lower latency than System A. *Pilot evidence (2026-10-06 note): H2 is mixed — storage does not hold for app size (Qwen2.5-1.5B adds ~890 MB to the app, while Apple's model is built into iOS and adds 0 MB to the app); for latency, Qwen has a much lower time-to-first-token (~0.2s vs. ~1.3s) but a similar total response time (~7–8s). Report both honestly.*
- **System A:** Apple Foundation Model + RAG + structured memory.
- **System B:** open-weight LLM (via Apple's Core AI framework) + RAG + structured memory — currently **Qwen2.5-1.5B-Instruct** (since 2026-09-30, on-device verified); the earlier Qwen3-0.6B is archived (`ArchivedModels/`) and kept as the small-model data point. See findings below.
- Both systems must share: the same knowledge source, the same retrieval pipeline, the same prompt structure. **In the experiment, the retrieval step is an oracle:** `BatchRunner` pins the correct document via `selectedMaterialID`, so `TutorViewModel.referenceDocument(for:)` (`ContentView.swift`, the explicit-pick branch) bypasses `KnowledgeRetriever` and inserts the whole document into the prompt. The study therefore measures the **generation stage** of RAG — see "RAG scope clarification" (2026-09-30).
- Metrics — primary (inferential): pass@1. Secondary (descriptive): time-to-first-token, total response time, tokens/sec, model storage size, thermal state.
- Grounding references: Liang et al. 2022 (HELM, Stanford CRFM — multi-metric evaluation, no single model wins everywhere). See the 2026-09-23 entry below for the expanded reference list (pass@1/contamination/canary-task precedent) added with the pivot away from education framing. Modran (2025), previously cited for MCP/ACP adaptive tutoring, was dropped along with that framing.

**Core AI (System B) — technical findings (2026-08-30):**
- Requires iOS 27 / macOS 27 / Xcode 27.
- Open-weight models are exported to Apple's `.aimodel` format via the open-source `coreai-models` Swift package (`github.com/apple/coreai-models`); a ~0.6B-parameter model is documented as a good first choice for on-device.
- `coreai-models` ships `CoreAILanguageModel`, which conforms to the same `LanguageModel` protocol as Apple's built-in Foundation Models. `LanguageModelSession(model: CoreAILanguageModel(resourcesAt: modelURL))` is a drop-in replacement for `LanguageModelSession()` — identical `respond(to:)`/streaming API. System A and System B can therefore share one engine (prompt construction, RAG injection, memory injection) and differ only in the `model:` passed into the session — the intended seam for the comparison harness.
- `LanguageModelSession.Usage` reports token counts; latency needs manual wall-clock timing. Ahead-of-time compilation (`coreai-build` CLI → `.aimodelc`) exists to exclude one-time model-specialization cost from latency measurements.

**Decision (2026-08-30):** deferred adding struggling-topic re-ranking to `KnowledgeRetriever` (Modran-et-al.-style MCP re-ranking — fuses semantic similarity with session context; reported Recall@1 0.42→0.64 in their study) — retrieval is shared/controlled between System A and B, so it can only move both systems' absolute accuracy numbers, not which one wins; not worth tuning with no System B yet to compare against. **Priority: build System B before further RAG tuning.**

**RAG-vs-judge debugging pass (2026-09-10):** before chasing suspected judge issues (prompt-injection-style concerns raised in a research meeting), verified the RAG delivery pipeline first, on the reasoning that oscillating between two unverified suspects (RAG vs. judge) wastes effort — check the shared/controlled layer before the less-controlled one. Evidence gathered from the real 40-Q&A transcript (`evaluation/prototype-on-device-transcript-1788397220.json`):
- Retrieval and prompt delivery confirmed clean: the same single 1,135-character document was retrieved and fully injected into the prompt for every one of the 40 messages, on both systems, well within Core AI's 4096-token context limit. Ruled out as the cause of any downstream scoring problems.
- Root-caused the "answer duplication on 2 answers" finding from 2026-09-03 above: `FoundationModelsTutorEngine`'s incomplete-response continuation fallback (triggered when a reply doesn't end in `.!?`) fired on exactly 2 of External's 20 replies — evidenced by those 2 messages' `inputTokens` being roughly double the normal ~380-token baseline (the session's accumulated `usage` includes the follow-up call's reprocessed context). Apple's model never triggered this path across all 20 of its replies.
- Deeper cause of *why* the fallback fired on those 2 at all: both replies were already complete, but ended in a trailing markdown bold marker (`**concluding phrase.**`) rather than bare `.!?` — a Qwen3-0.6B stylistic habit not seen in any of Apple's 20 replies. The fallback's completion check (`endsWithSentenceTerminator`) only recognizes `.!?` as the last character, so it misclassified these already-finished replies as incomplete, triggered the "please continue" re-prompt, and the small model — having nothing left to add — simply restated its conclusion, producing the duplicate.
- **Fix implemented and build-verified only (not yet confirmed on-device):** the continuation block in `FoundationModelsTutorEngine.streamResponse` (`ContentView.swift`) now discards the follow-up if it's a near-duplicate (trimmed containment check both ways) of the already-generated text, instead of blindly appending it. Falls through to the existing `isIncomplete`/Retry UI in the duplicate case. Both backends still share identical engine logic — only the validation of the follow-up changed.
- No evidence found of judge-side prompt injection; that hypothesis was never tested and remains open, not ruled out. The `endsWithSentenceTerminator` markdown blind spot (trailing `**`/backticks not recognized as terminators) is also still open, not yet patched.

**Pivot: RAGAS/LLM-judge → pass@1, and away from education framing (2026-09-23):**
- Dropped the programming-education framing in favor of a general on-device backend comparison — avoids needing human-subject/learning-outcome data, and lets the study focus purely on system/model comparison.
- Replaced the RAGAS-style LLM-judge (faithfulness/answer-relevance/context-relevance, used in the 2026-09-03 study above) with pass@1 (execution-verified code-task success) as the primary metric. Motivation: LLM-judge scores are judge-dependent in practice, not just in theory — switching Gemini→Anthropic on 2026-09-03 required rubric changes and shifted scores. pass@1 removes that dependency and gives a hard, binary control (a no-RAG answer to a fictional/canary spec either passes or fails — no partial credit).
- New pass@1 dataset: code-generation tasks paired with fictional ("canary") documentation — invented specs (e.g. a made-up serialization format, a made-up rate-limiter class) so a correct answer requires the RAG pipeline to have actually delivered and been used, not memorized from pretraining. Mirrors published contamination-avoidance methodology rather than using HumanEval/MBPP directly (those have documented 8–18% contamination in open pretraining corpora — see references below).
- **Dataset progress:** 13 of 40 planned tasks authored and validated (`evaluation/tasks/*.json`; categories: data_format 10/10, api_usage 1/9, validation_rules 1/9, bugfix_completion 1/9) — 27 remain. *(Target revised 2026-09-30 to 10 per category — api_usage/validation_rules/bugfix_completion each 1/10; the 9-per-category plan only summed to 37.)*
- **Known dataset issue, not yet fixed:** `task_004_merge_intervals` passed under the no-RAG condition in a real on-device run (Apple backend) — "merge overlapping intervals" is a well-known generic algorithm the model may already know, undermining the "unsolvable without the document" design intent for that specific task. Needs a per-task no-RAG check before the 40-task set is finalized. *(Superseded 2026-09-25: kept and reported as a finding rather than replaced — see that entry.)*
- **Tooling built**, all outside the Xcode project in `evaluation/` (same on-device-exemption precedent as `score_transcripts.py`, see Architecture Rule #1): `code_task_runner.py` (sandboxed, timeout-guarded execution of candidate code against a task's test), `validate_tasks.py` (confirms each task's own reference solution passes its own test before use), `score_code_tasks.py` (extracts the fenced code block from an exported transcript answer, runs it via `code_task_runner`, reports pass@1 by system and by with/without-RAG condition — inferred from whether `retrievedContext` is present on that message, not a manual flag).
- **New methodology references:** Chen et al. (2021), arXiv:2107.03374 (pass@k/HumanEval origin); Carlini et al. (2019, USENIX Security) (canary-based memorization auditing); Riddell, Ni & Cohan (2024), arXiv:2403.04811 (HumanEval/MBPP contamination quantification); Liu, Zhang, Jin & Neville (2026), arXiv:2605.08838 (leakage-free synthetic RAG benchmarks); Fang, Ding, Mastropaolo & Xu (2025), arXiv:2506.22776 (quantized LLM code-gen robustness); Salem, Algraeeb, Al-Nihmy & Mazzara (2026, AINA/Springer) (RAG improves weak on-device LLMs — edge-device benchmark); Artificial Analysis (2026), Mobile Device Benchmark Set methodology (pass@1 on quantized on-device models).

**Core AI reliability finding — Qwen3-0.6B-static fails deterministically on code-generation tasks (2026-09-22/23, extensively investigated, root cause still open):**
- Across 3 full on-device runs (13 tasks × 2 backends × 2 RAG conditions each), External (Qwen3-0.6B, `mixed_4bit_8bit_static` export) fails with `GeneratedContent.ParsingError` ("Failed to parse generated content") on ~38% of no-RAG code tasks and ~85–92% of with-RAG code tasks. Apple's backend does not exhibit this.
- **Hypotheses tested and ruled out, each with on-device evidence:** (1) special notation in the RAG documents (`<`, `~`, `{}`) — 3 isolated diagnostic prompts with the same notation did not reproduce the error; (2) prompt length alone — a long plain-prose document + code request also didn't fail; (3) cumulative session/call-count degradation — failures are deterministic and tied to specific task IDs, not position in the session; (4) thermal throttling — the exact same tasks fail identically across runs with different thermal histories; (5) a stale/cached build — `Product > Clean Build Folder` + re-run produced identical failures.
- Found a closely related, upstream-acknowledged bug: `apple/coreai-models` issue #247 ("Guided generation refused... on static-shape (iOS) exports"), fixed by PR #248 (commit `3e172fb`, merged 2026-09-14). Updated the project's pinned `coreai-models` commit from `de31ba5` (2026-08-28, pre-fix) to `0f0ce65` (2026-09-22, includes the fix) — required refreshing a stale **global** SwiftPM cache, not just the project's `DerivedData`/`Package.resolved` (see Environment Notes). **Result: no change** — identical failures, byte-for-byte, before and after the update. The upstream fix does not address this failure mode; root cause remains open.
- Failures are fully deterministic given the same prompt+task: the same task IDs fail every time, with byte-identical output, across all 3 runs (different thermal states, different `coreai-models` versions) — this is what rules out (3) and (4) above with high confidence, not just plausibly.
- **Decision:** stop further root-cause debugging of this specific model export. Export `Qwen2.5-1.5B-Instruct` as a second System B variant (already planned, see 2026-08-31 entry above) to test whether this is specific to Qwen3-0.6B's quantization/export, or general to small quantized models on Core AI. Not yet started.

**Core AI failure root-caused and fixed; "Swift" prompt bias removed (2026-09-28, on-device verified across 2 full runs):**
- **Root cause:** Qwen3's chat template leaves **thinking mode on** by default (`enable_thinking` unset), and `coreai-models` never disables it. With reasoning support detected, `CoreAILanguageModel` allows 2048 output tokens; on code tasks the 0.6B model spent the entire budget inside hidden `<think>` reasoning and never emitted an answer. Reproduced on macOS 27 via a SwiftPM harness running the exact app code path (task_001 with RAG: 2048 output tokens, **2047 of them reasoning**, 0 visible chars). The iPhone surfaced this as `GeneratedContent.ParsingError` ("Failed to parse generated content"); the Mac as "Session ended without producing a response." The error is thrown by FoundationModels, not by `coreai-models` (the string does not appear in the package source). Not the package's parsing, not the model's coding ability — this also explains why failures were deterministic (see sampling note below) and more frequent with RAG (longer prompts → longer reasoning).
- **Fix:** `FoundationModelsTutorEngine.streamResponse` now appends ` /no_think` (Qwen3's official soft switch) to the prompt, and to the continuation follow-up, **only when the backend is Core AI** — Apple's prompt is unchanged. **Pre-specified analysis plan for H1 (fixed 2026-09-30, before any data for tasks 14–40 exists — do not change after that data comes in):**
- **Why fix it now:** the same data admits several valid analyses with different p-values (run 1 alone p≈0.13, run 2 alone p≈0.23, pooled per-answer p≈0.04). **RAG scope clarification (2026-09-30) — what "RAG" means in this study:**
- **What's measured:** the **generation stage** of RAG under **oracle retrieval** — for every task, both models receive the correct spec document in full (pinned via `selectedMaterialID`; `referenceDocument(for:)` returns the pinned document before ever calling `KnowledgeRetriever`). The retriever itself is **not** evaluated. The app's semantic retriever (`KnowledgeRetriever`: `NLEmbedding` sentence embeddings, 400-character paragraph chunks, cosine distance, untuned 0.9 relevance cutoff) exists and is used in normal chat, but the batch experiment never exercises it. In the experiment the prompt is: structured-memory line → `Reference material:` + the full document (~1k characters, no chunking, far below the 4096-token context) → shared instruction + task prompt.
- **Why this is valid for H1:** (1) controlled comparison — retrieval is identical and ideal for both models, so pass@1 differences come from the model, not the search; (2) approximates ideal retrieval — the oracle setting is *typically treated as* an upper bound for retrieve-then-generate pipelines (real retrieval errors such as missing/irrelevant chunks would usually lower both scores), but **not a strict guarantee**: CodeRAG-Bench found retrieved documents sometimes matched or beat gold documents, and a 2026 study found iterative RAG can beat gold context — so never call it a strict upper bound in the paper; (3) evaluating retrieval and generation separately is standard RAG-evaluation practice (e.g. RAGAS scores context and answer separately; CodeRAG-Bench reports code pass@1 with and without gold documents); (4) it answers the "RAG isn't standardized" critique raised by researchers from another university: retrieval choices (chunking, embeddings, top-k, re-ranking) vary across studies, so this study holds them constant and fully specifies every RAG setting (knowledge source, oracle retrieval, no chunking, identical prompt template, temperature 0.2, 1024-token cap, no-RAG control) for reproducibility.
- **Terminology and references (verified by web search 2026-09-30):** the literature uses several names for the same setting — "oracle document(s)" (RAFT: Zhang et al. 2024, Berkeley, "Adapting Language Model to Domain Specific RAG", oracle vs. distractor documents); "oracle retrieval / oracle context / Oracle-RAG" (CRUX, arXiv 2506.20051; FinanceBench retrieval-failure study, arXiv 2602.17981); "gold context / gold documents / gold passages" ("When Iterative RAG Beats Ideal Evidence", arXiv 2601.19827; CodeRAG-Bench); "canonical documents" (CodeRAG-Bench: Wang et al., NAACL Findings 2025, arXiv 2406.14497). "Oracle document" alone is rare as a search term — search "oracle retrieval" RAG or "gold context" RAG. **CodeRAG-Bench is the closest precedent to cite:** it reports code-generation pass@1 without documents vs. with gold (ground-truth) documents, using temperature 0.2 (same as this study). Recommended paper phrasing: *"Retrieval was held constant using an oracle (gold-context) setting, in which the correct reference document is supplied in full (cf. RAFT; CodeRAG-Bench)."* These papers commonly run **three settings** — no context (lower bound), gold/oracle context (ideal retrieval), and the real retriever (in between); this study has the first two (no-RAG control + main experiment), and the optional retriever-only test below would partly cover the third.
- **Wording rules for the paper and talks:** say "the generation stage of RAG, with retrieval held constant (oracle document)" and "the same retrieval-augmented prompt"; describe the experiment's document as "provided" or "oracle", not "retrieved"; never write "we evaluated the RAG pipeline" without that qualifier; "with RAG / without RAG" (or "with / without the document") is fine. Ready-made introduction sentence: *"My app is a full on-device RAG system: it stores documents, searches them, and inserts the relevant one into the prompt. In this experiment I hold the search step constant by giving both models the correct document, so I'm measuring the part of RAG that depends on the model — turning the document into a correct answer."*
- **Limitation text:** *"Retrieval was held at an oracle setting (the correct document supplied in full) to isolate model behavior. Real-world retrieval errors were not evaluated and would likely lower both systems' scores; evaluating the on-device semantic retriever is left for future work."*
- **Optional future work (not started; needs a pitch before any code):** a retriever-only test — run `KnowledgeRetriever` on the 40 task prompts against all 40 spec documents and report Recall@1 (how often it picks the correct document). No language-model generation, no phone heat/battery cost, possibly runnable on the Mac, and separate from the frozen main-study protocol. A fuller third condition (models answering with whatever the retriever picked) would cost ~200+ more on-device answers — only after the main study.

**Thermal cost of on-device runs (2026-11-03; offline, descriptive; branch `feature/thermal-analysis`):**
- **Why:** a deployment cost that pass@1 and latency medians hide — how much of a run the phone spends cooling, how fast it heats up and how long it takes to recover. Requested by the researcher as material for explaining the drawbacks of a big on-device model; no app or protocol change.
- **Method (`evaluation/thermal_analysis.py`):** each exported answer has its start time (the assistant message's timestamp, to the second), `totalTime`, and `thermalState` at start and end. A gap between consecutive answers in a block, minus `BatchRunner`'s fixed 3 s pause, is time spent in `waitIfHot` (waiting until Fair). Across all runs, normal gaps are −1…+1 s (2,625) and every real wait is ≥ 15 s (231), so the 4 s threshold is unambiguous. The counts reproduce every thermal number already in this log (e.g. H1b: 3 capped waits, 2 answers started at Serious, 57 ended at Serious; unpaced pilot run 1: 179 of 260 started at Serious). Gaps between blocks (Core AI preload + 2-min cool-down + wait-until-Fair) are reported separately, not counted as waits.

- **Name:** Prototype On-Device
- **Purpose:** University research investigation (Tec de Monterrey) comparing two on-device AI backends — Apple's native Foundation Model vs. an open-weight LLM deployed via Apple's Core AI framework — each given the same retrieval-augmented prompt and structured memory (a student-profile line — part of the study protocol, removed from the app on 2026-11-16 after all data was collected) (retrieval held constant via an oracle document — see "RAG scope clarification" in the Research Design & Decisions Log), evaluated on RAG-grounded code-generation tasks via pass@1 (execution-verified success). This codebase is dedicated to that research/comparison harness; it is **not** the tutor product (that has been split off as a separate project). - **Core frameworks in play:** FoundationModels (generation), PDFKit (PDF text extraction), Vision (OCR for imported photos), NaturalLanguage (`NLEmbedding` sentence embeddings for semantic retrieval), Speech (voice input).
- **Audience:** this is a school investigation project, not a production app. Explanations of concepts (RAG, embeddings, Foundation Models, etc.) are often requested in language suitable to present to a teacher — default to clear, simple-then-technical explanations rather than assuming deep prior ML/AI knowledge, unless told otherwise.
